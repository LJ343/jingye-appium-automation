# Wireless recovery repair 0.2-review

This sanitized source tree preserves the USB main baseline and overlays six reviewed runtime files. The two changed runtime files have now been deployed with backups and fresh idle checks; this is a bounded acceptance, not a completed long-term unattended guarantee. APKs are distributed separately as release assets; private configuration, credentials, accounts, phone identity, endpoints, logs, signing keys and build dependencies are excluded.

Two newly diagnosed gaps are addressed in this revision:

1. A wireless ADB endpoint could change after Appium Remote succeeded but before the program captured its phone-process ownership evidence. The old capture rejected that change, then normal quit could return HTTP 200 while UiA2 remained, leaving the durable guard uncertain. The repair retains immutable creation and capture transports separately. On a changed endpoint it requires this Remote's exact ownership token read back from the active UiA2 session, a matching session UUID, the listening socket's UID/inode matched to the process file descriptor, and stable PID/UID/start-time/cmdline/instrumentation evidence. Only after proof succeeds may it perform normal quit, one precisely scoped TERM if needed, complete physical-cleanup verification, guard closure and a fresh Remote attempt. Unknown or mismatched ownership remains blocked. A shared finite deadline bounds read-only reconnection and proof retries; it does not replay unknown creation or kill unknown processes. Same-shell identity rechecks reduce the stale-PID window but are not kernel pidfd atomic binding.

2. Companion 0.1 could permanently pause and remove its observers when Android did not keep wireless debugging enabled. Later external recovery of the actual switch therefore did not re-arm it. Companion 0.2-review now retains a read-only WAIT_EXTERNAL_ON state and observers after that soft failure. It performs no repeated setting writes while waiting. An externally restored switch and available Wi-Fi must remain observed for a complete 30 seconds before re-arming. User stop, permission/platform faults and the write-rate circuit breaker remain hard stops. Network trust confirmation remains Android's normal user decision.

Offline acceptance: 213 actual runtime tests passed (141 reconciliation, 59 general connection/discovery/guard, 13 platform), including 16 new ownership and recovery cases. The companion's actual controller and failure-boundary code passed 31 deterministic Java tests. Independent review added 9 companion cases. These checks do not simulate every OEM interface or replace live acceptance.

The companion has versionCode 2 and versionName 0.2-review, with unchanged permissions. Its reviewed raw source aggregate is 6a522773afb52f5a3520dd2bacf341ed1e3259833fb06e0406dbaac487866b5b. The same-certificate 0.2-review APK was built and verified separately. The controlled live pre-capture endpoint-change trial passed: the first Remote returned before ownership capture, one induced wireless-debugging interruption changed the endpoint, the exact live session token and socket/process proof were recovered, normal quit returned HTTP 200, one owned TERM was followed by complete physical cleanup and guard closure, and a second Remote and normal quit completed with no signal. Both session DELETEs returned HTTP 200 and final lifecycle auditing passed. No login, business collection, platform upload or service restart was part of that diagnostic. A separate post-fix synthetic transfer check verified 202/202 pulls of 202 unique fixtures with zero failures, without a new fault injection. The deployment preserved the existing schedules, host births and four other runtime files. The matching companion APK and verification files are distributed as separate Release assets.

Prior scoped checks included 606 synthetic file transfers over three full rounds, a controlled trusted-network Wi-Fi interruption, screen-off observation and a representative account crawl. They predate this repair and are not acceptance evidence for either new fix. No 24-hour uptime, phone-reboot recovery, recovery from system force-stop, uninterrupted multi-hour business execution, or automatic approval of an unknown network is promised. The companion cannot turn Wi-Fi back on. Android/OEM restrictions, network trust prompts and App risk controls can still require intervention. A wireless-debugging switch value of 1 is not proof that the computer is connected to the intended phone.

Collection scope, dates, persistence, upload rules and delivery contracts are unchanged. Every entrypoint must inherit JINGYE_WIRELESS_ENABLED=1 and its private JINGYE_WIRELESS_CONFIG. All callers must use the same canonical appium_guard_path; never use a fresh guard to bypass uncertainty. Do not run diagnostics concurrently with production. Deploy only after fresh acceptance and a reviewed rollback receipt. See the companion README for visible stop controls, permission effects and revocation.

Companion 0.2 was installed as a same-certificate update; the installed APK hash matched the release artifact. Its visible Start control, foreground service, existing grants and USB-off/TLS-on state were verified. The new passive external-ON timing boundaries were checked by the deterministic Java tests; they were not separately reproduced on this OEM phone.
