# Failed wireless session creation recovery — 2026-11-13

A wireless link can disappear while Remote is still starting UiAutomator2. Previously, even a complete instrumentation-start HTTP 500 was recorded as creation_unknown, so the existing second creation attempt was never reached and the persistent guard blocked the next run.

The desktop now checkpoints the same local Appium host's startup log after the verified idle-phone baseline and before Remote. Recovery requires a single exact opaque token-bearing request, a complete HTTP 500 for instrumentation initialization, no master addition or competing mutation, and a paired master/deletion lifecycle in the earlier log prefix. The prefix is audited only on failure and cached for that one witness; ordinary healthy creation reads only a small header/checkpoint. Logs must have a unique birth-matched filename, stable file identity/header, a complete bounded suffix and the same freshly verified PID/birth host. Missing evidence keeps the existing unresolved guard.

This supports Appium 3 with session_discovery disabled: it does not treat GET /sessions 404 as empty, enable an insecure feature, change official code, or restart the host. The actual downstream UiA2 GET /sessions remains a separate protocol check. Before any failed-launch residual signal, it must be empty and belong to the exact stable PID/UID/startTicks/cmdline and listener inode, with one verified test instrumentation. A temporary exclusive forward is removed precisely. Only that proven launch's process receives one TERM with immediate run-as identity rechecks. Active/foreign sessions, ambiguous ownership, changed hosts/sockets/identities, incomplete logs or lost mutation responses stop recovery. There is no package-wide force-stop. A lost signal/allocation response is never replayed.

Physical process, instrumentation and owned forward counts must all reach zero before the same-owner same-host failed-creation guard can be closed. Only then can the existing maximum of two Remote attempts continue; connectivity is discovered and verified again before the next attempt. Normal active-session cleanup still requires explicit quit and its original ownership checks. Pre-checkpoint historical markers cannot use this path or be backfilled with invented evidence; they require separate explicit reconciliation.

Wireless sessions also set appium:disableSuppressAccessibilityService=true so the explicitly enabled connection helper remains available during UiAutomation. This is a supported driver capability, not a change to the helper APK or an assertion that accessibility suppression caused a particular outage. See the [official capability reference](https://appium.github.io/appium-uiautomator2-driver/latest/reference/capabilities/#disablesuppressaccessibilityservice).
