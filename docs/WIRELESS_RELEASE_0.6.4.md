# 0.6.4 candidate — live acceptance pending

This candidate has passed offline checks and a same-signer APK build. It has not yet passed installation verification or HONOR live pairing acceptance. Production wireless and USB branches remain unchanged.

## Exact Wi-Fi-name trust

The existing per-AP list remains valid. A separate foreground action adds an exact Wi-Fi name, including case, spaces and Unicode, and explicitly confirms trust for all APs with that exact name. There is no prefix, wildcard or automatic network import. Only a digest is stored. Adding a name does not grant Android system trust by itself. Both modes use the original shared click budgets and recheck the actual current AP before each action. Removing a name preserves per-AP entries; clearing per-AP entries preserves names and disables auto-confirmation. Location permission/system location remain necessary to identify the current Wi-Fi.

## Automatic re-pairing

The default is disabled. A healthy verified connection returns normally without opening Settings. Recovery first uses existing connections, mDNS, cache and the bounded single-phone port discovery. An actual authentication failure for a fresh HMAC-authenticated phone IP can authorize a request. A separate explicit desktop opt-in, `allow_verified_discovery_repair: true`, also permits a request after a completed unsuccessful discovery sweep while the same phone IP still has a fresh authenticated report. A single offline/refused/timeout result or an incomplete sweep is insufficient. The phone requires the v2 foreground policy approval introduced in 0.6.2. Existing approved 0.6.2/0.6.3 settings retain that approval; a legacy enabled flag from 0.6.1 alone is insufficient.

The original configured computer signs a short-lived request with the existing private address-channel key. With independent foreground approval in the helper, the first authenticated request fixes that computer's original ADB public-key fingerprint; later different host keys are rejected. No ADB key is regenerated. Installation alone does not enable pairing.

On an unlocked, interactive phone, with helper/accessibility active and an explicitly trusted AP or exact name, the helper opens the official system developer/wireless pairing page. It accepts only identified system Settings windows and exact recognized controls. The one-time code and pairing endpoint are AES-256-GCM encrypted using a separately derived key and request/host-bound additional authenticated data, then authenticated on the existing address UDP channel. They are not written to diagnostic records, clipboard, command line or files. While an authenticated request/code is in flight, the computer pauses slow discovery to prevent code expiration. It supplies the code to the pinned existing-server ADB client through stdin. Only after successful pairing, a matching offline transport for that exact authenticated connection endpoint may be disconnected once; online/other endpoints are untouched. It then separately verifies the connected phone identity. A successful pair command alone is insufficient.

On the recognized, platform-signed developer-options page only, the helper reserves at most six scroll actions in one request (including an advertised scroll-to-top action when available), against one identified list. Other pages and ambiguous lists cannot scroll. Scrolling does not touch debug switches. The flow lasts at most 30 seconds and is limited to two persisted requests in ten minutes. No permanent pairing-page polling occurs. It does not unlock the phone, approve unlisted networks, remove other pairings, disable protection, change business rules or restart any service. An unknown OEM interface fails closed and requires a compatibility fix; support must be demonstrated on the actual phone.

## First upgrade while currently unpaired

1. Download and verify the APK from this prerelease. Install as an update using the normal phone installer; do not uninstall or clear data. Existing private address configuration and AP entries must be retained.
2. Open 0.6.4. Add the exact company Wi-Fi name if desired; retain the original per-AP entries. Enable the existing whitelist auto-confirmation and check Android accessibility remains enabled for this helper.
3. Confirm “本电脑自动重新配对” remains enabled. Existing approved 0.6.2/0.6.3 settings need no renewed approval. First-time users or users upgrading from 0.6.1 must enable it and read the foreground confirmation. The fixed host and retry ledger are preserved. This permits the original authenticated address-channel computer to pin its own existing debug key once. Keep the phone unlocked during live acceptance. Do not generate or send a pairing code manually.
4. The maintainer runs connection-only acceptance from the candidate layer. This opens official Settings when authenticated recovery is required. No Appium business session or collection is started.

The desktop optional `pairing_recovery` configuration has `enabled`, `host_key_sha256` (SHA256 of the original 524-byte decoded adbkey.pub token), and an absolute private `ledger_path`. These are local settings and are not provided in this public export. The shared address-channel secret remains private. Python cryptography 48.0.0 was observed and tested; it is only imported for this enabled feature.

## 0.6.3 live observation and 0.6.4 entry compatibility

The genuine 0.6.3 request reached `PAIR_WIRELESS_DETAILS_NOT_VISIBLE` without an encrypted-code receipt or pairing command. The user then independently confirmed the actual phone was on wireless-debugging details and both the connection-address row and the pairing-code entry were visible. This establishes that navigation entered details; it does not identify the actual OEM view ID, which was not dumped over ADB.

0.6.4 removes the standard title-ID requirement only for the pairing entry. Before selecting it, the helper independently requires a recognized official wireless-details toolbar title and exactly one connection endpoint matching the fresh authenticated phone IP. It matches the exact public pairing-entry label in text or accessibility description and requires one enabled, non-checkable, non-scrollable preference action in the same window. Duplicate labels for one physical action are deduplicated; multiple distinct actions fail closed. Root/list/toolbar/switch/checkbox/edit targets are refused. The root and target are refreshed, and the same details/address/action are rechecked immediately before the single click.

The original exact-ID pairing fields remain supported. An OEM field fallback additionally requires the already-requested official pairing dialog and an exact public Wi-Fi/WLAN pairing-code marker. Only one six-digit value and one same-authenticated-IP pairing endpoint distinct from the captured connection endpoint are accepted. Both values remain transient and use the existing request-bound encrypted exchange. Focused system-type Settings dialogs are eligible for reading only after the authorized code-page click. Foreign/background/ambiguous windows remain blocked. Traversal is bounded by 512 visible owned nodes and depth 35, with incomplete snapshots rejected; no partial positive selection is used.

Fixed failure stages now distinguish unrecognized details title, missing/ambiguous/actionless pairing entry, stale or changed target, unrecognized code dialog/marker, ambiguous code/address and incomplete tree. Diagnostics contain no UI text, address, port or code. No new permanent polling, permissions, service control, unlock, network trust scope or business changes are introduced. Existing v2 foreground approval, original host key, trust lists and persisted limits are retained. Do not clear app data or re-register lists when upgrading from an approved 0.6.2/0.6.3 setup.

347 Python tests and 294 helper assertions passed, including 49 entry/field cases running the production selector against in-memory Android test trees. Same-signer APK/source checks passed. These synthetic cases do not prove the actual HONOR entry, field extraction, encrypted return or end-to-end pairing. Live acceptance remains required before production deployment.
