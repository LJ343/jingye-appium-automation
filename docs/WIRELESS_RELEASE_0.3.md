# Wireless recovery 0.3-review — 2026-11-06

The previous recovery code could rediscover a changed port only at the configured phone IP. The phone acquired a different Wi-Fi IP, outside that one-IP scope. Connecting once to its current endpoint and checking the same-phone identity succeeded without pairing again. The failed historical run did not independently record the phone IP at the failure instant; this diagnosis does not invent a full historical network timeline.

0.3 adds an authenticated phone-to-PC address report. The computer listens only while existing connection recovery has failed, selects one authenticated phone IP, discovers its port within the existing bounded range, and verifies the expected phone identity before continuing. A MAC-protected verified endpoint cache lets the read-only status command follow that IP. There is no subnet scan, permanent PC receiver, auto-pairing, host service restart or change to business dates, collection, database, upload or email rules.

The Android companion retains the 0.2 setting-recovery policy byte-for-byte. INTERNET is the only newly added permission. Provisioning is local and private; no shared key is built into the APK or published. The handshake uses HMAC-SHA256, a fresh challenge, source IP/port binding and expiry. Reporting occurs only while armed, Wi-Fi is present and the switch is enabled, at most once per 15 seconds with a two-second exchange limit. The existing switch write-rate limits and Android network-trust decisions remain.

Deployed evidence: same-signer 0.3 APK installed and its actual bytes verified; reporter configuration, foreground service, existing grants, USB-debugging off and wireless-debugging on checked. A real authenticated report and single-IP port discovery succeeded with same-phone identity, with the isolated test deliberately ignoring existing transport/cache candidates but not disconnecting them. Discovery took 33.469 seconds. Three connection/status files and private connection configuration were deployed, final checks passed, and temporary UDP listening ended. ADB, Appium and OpenClaw host instances stayed unchanged. The normal status command returned CONNECTED.

Validation before deployment: 81 Python tests, 31 original helper state tests, 9 external-wait tests, 12 Java protocol assertions and a shared Java/Python protocol vector passed. The sanitized exported source is separately regression-tested before publication; 250 exported Python cases (96 general, 141 reconciliation, 13 platform), 31 + 9 helper cases, 12 protocol assertions and the shared Java/Python vector passed. See [export validation](ADDRESS_REPORT_VALIDATION.json) and the runner.

Limits: actual natural phone-IP changes were not reproduced during this live trial. No business rerun, new long business acceptance, phone reboot, force-stop recovery or arbitrary network guarantee is claimed. The companion must be armed and alive, original pairing trust valid, authorized Wi-Fi range and both network directions reachable, and fixed PC address/firewall scope correct. Production retained its existing 37000–50000 scan range and 300-second budget; random ports outside that range can still fail. Idle status viewing never initiates reconnection. The helper's PC_UNVERIFIED state describes the phone switch, not the PC's ADB connectivity.

The 0.2 release remains available. The older docs/WIRELESS_RELEASE.md and USB text describe historical revisions. main is unchanged. See ../android-companion/ADDRESS_REPORT.md for configuration and revocation.
